## Blocking Issues
- **`psycopg-pool` is missing from `requirements.txt`.** The API imports it at startup; without
  it the server still boots and answers `/v1/health`, but reports `database: false` and every
  schedule/plan/admin route returns 503. The only clue is one line in the log: `database
  unavailable at startup: No module named 'psycopg_pool'`. `psycopg[binary]` does **not** pull it
  in. Fix: add `psycopg-pool==3.2.3` (installed into the local venv this session, but
  **`requirements.txt` has not been edited** — awaiting owner approval).
- **6 tests fail.** All in `tests/integration/test_forecast_admin_api.py`, all on `/v1/plan`. The
  one-transfer planner (commit `089ad92`) emits a new `WITH board AS (...)` query, and the
  hand-written DB double in that test raises `AssertionError: unexpected SQL in API test`. The
  stub is deliberately built to fail loudly on new production SQL, so this is the feature having
  shipped without its test double updated. The new transfer query is therefore **untested**.
- **No clock control.** `api/deps.now()` and the simulator both use real time, so only the
  current hour can be demonstrated. Showing a full day — morning crush, midday, evening peak,
  late-night lull — remains impossible. Unchanged from the previous session and still the
  highest-value demo item.
- **There are no passenger accounts of any kind.** No signup/register endpoint exists — the only
  roles are `OPERATOR` and `CONDUCTOR`, and `provision_user()`'s docstring states it exists to
  provision staff "without exposing a signup API". The passenger profile screen is entirely
  static: a hardcoded avatar for "Mayank Tiwari" fetched from `ui-avatars.com`, literal stats
  (`142` trips, `₹450` wallet, `18kg` CO₂), and a Logout button wired to `onPressed: () {}`.

## Environment Notes
- **Two machines now.** The owner's original notes describe `C:\...\jishu\...` with the recorded
  MBTA corpus. This session ran on a second Windows 11 machine with the repo at
  `D:\pravaah-dev\pravaah` (kept off `C:` — that drive had under 2 GB free; the TimescaleDB image
  alone is 4.05 GB). Flutter SDK at `D:\pravaah-dev\flutter`, venv at `<repo>\.venv`.
- Modules must run from `src/` (`cd src && python -m pravaah...`); `pyproject.toml` sets
  `pythonpath=["src"]` for pytest only, not for `-m`.
- **Redis must be 7+.** A native Windows `redis-server` (the old 3.0.x port) was already holding
  6379 and does not implement `GEOADD`/`GEOSEARCH`; the simulator and API both crash on it with
  `unknown command 'GEOADD'`. Worked around by running `redis:7-alpine` on **6380** and setting
  `PRAVAAH_REDIS_URL=redis://localhost:6380/0`, leaving the existing Redis untouched.
- **The `timescaledb-ha` image needs a `pg_hba` rule added by hand.** It does not honour
  `POSTGRES_HOST_AUTH_METHOD`; out of the box only in-container loopback is trusted, so host
  connections fail with `no pg_hba.conf entry for host "172.20.0.1"`. It also does not support
  SSL, so `sslmode=require` is not a way around it. Additionally its `pg_hba.conf` contains 32
  **NUL bytes**, and Postgres stops parsing at the first one — an appended rule is silently
  ignored until the NULs are stripped. Fix applied: strip NULs, append
  `host all all all scram-sha-256`, `SELECT pg_reload_conf()`.
- `PRAVAAH_AUTH_SECRET` must be ≥32 bytes or every login returns 503. It fails closed by design —
  there is no fallback dev secret.
- Docker Desktop's WSL VM shut itself down mid-session (both distros showed `Stopped`), which
  presents as `docker` CLI commands hanging indefinitely rather than erroring.
- Do not use `pkill -f uvicorn` — it matches and kills the agent's own shell.

## Known Issues / Tech Debt
- **Every Delhi number is an ASSUMPTION**, marked as such in `config/cities/delhi.toml` and
  `sim/demand.py`: capacity 35 seated / 70 peak / 100 crush, the hourly demand curve, the weekly
  pattern, and arterial speeds. The research that produced them returned **citations whose URLs
  appeared fabricated**, so none were treated as sourced. Replace from the primary MoHUA Urban Bus
  Specification before any claim rests on them.
- **`/v1/plan` legs carry no `trip_id`**, only `board_stop_id` / `alight_stop_id`. The client
  therefore cannot fetch a leg's stop sequence and draws straight segments between landmark stops
  instead of following the road. Adding `trip_id` to the leg schema would let the journey map
  reuse the same `trip.stops` geometry the dashboard map already uses.
- **`src/pravaah/routing/` and `src/pravaah/features/` are empty** — `__init__.py` only. SOLUTION.md
  §25 reserves them and the directory map lists them, but the planner actually lives in
  `api/passenger.py` and there is no feature-construction module. Either implement them or record
  the deviation in SOLUTION.md Appendix C.
- **The route-and-position-specific model level is sparse** — ~126 cells against ~12,240 possible,
  so route-specific lookups usually answer from a coarser key and return `is_fallback: true`.
  Honest behaviour, and the UI must render it as "estimated from history", but "trained per route"
  would overstate it.
- **`docs/FRONTEND_HANDOFF.md` is rev 4 and documents 5 of 16 endpoints.** The app was built
  against a document missing two thirds of the API.
- The Flutter release build is **signed with debug keys** and still carries the template
  `applicationId = "com.example.pravaah_frontend"`. It cannot be distributed as-is.
- `docs/mayank.md` describes the app as "production-grade" with WebSockets/SSE streaming; there is
  no streaming anywhere in the codebase. Prose only, but it will not survive a judge's question.
- The recorded MBTA corpus (~1.3 GB) is git-ignored and is **not** present in a fresh clone; only
  `sim/calibrate.py` still references that data.
- `/v1/plan` now finds one-transfer journeys, so the `transfers` field is no longer always 0 and
  `fewest_transfers` can differentiate. Earlier notes in this file claiming otherwise were stale.
